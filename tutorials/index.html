What Is Claude Code?

Claude Code is an AI coding assistant made by Anthropic. It runs right in your terminal (that black window with the blinking cursor) and you talk to it in plain English. You describe what you want to build, and it writes the code, creates the files, runs commands, and debugs problems — all while you watch.

Think of it this way: You're the architect. Claude is the builder. You say "I want a four-quadrant task board with drag-and-drop" and Claude draws the blueprints, cuts the lumber, and hands you a finished product. If you don't like the paint color, you say "make it darker" and Claude repaints it.

What you'll build in this tutorial series:

  • Exercise 1 of 3: An Eisenhower Matrix — a personal task prioritizer you open in your browser
  • Exercise 2 of 3: A client homework form that emails responses to you via Google
  • Exercise 3 of 3 (The Big One): A middleware app that pushes data into a business system via API. This one comes in two versions and you only do one of them — take the QuickBooks version if your books are in QuickBooks Online, or the Contractors Cloud version if your jobs live in that CRM.
  • Then, page 5 — Harness & Memory: the settings, memory files, and habits that make every project after this one go faster

Each one is harder than the last. By the end, you'll be dangerous.

What you need to get started:

  • A Windows computer (you're on one — good)
  • Internet access
  • A Gmail account — if you don't have one, make one now at accounts.google.com/signup (free)
  • A credit card for a Claude subscription (flat monthly fee — no surprises)
Everything you'll sign up for, in one place — each link opens in a new tab, so you won't lose your place here: Claude (paid, Section 2) · Google account (free) · Node.js (free, Section 3) · GitHub (free, Section 7). Install Node.js

Claude Code is built on Node.js, which is a tool that lets JavaScript (a programming language) run on your computer. You don't need to learn JavaScript — you just need Node.js installed so Claude Code has something to run on.

Download Node.js
That button opens nodejs.org/en/download in a new tab. Node.js is free. On the page, choose Windows and the LTS release, then download the .msi installer.
On a company-managed computer? If an installer fails with a "cancelled" message you didn't cause, your IT security policy declined it for you — nothing is broken. Ask IT to install Node.js LTS; it's a routine request. (The same can happen with any install in these tutorials — watch for notes like this one.)
How do I know it worked? Open a Command Prompt (click the Start button and search for "cmd"), then type the command below and hit Enter. You should see a version number like v20.x.x or higher.
node --version
If it says "'node' is not recognized" — nothing is broken, your Command Prompt just started before Node.js did. Close that window, open a fresh one (Start menu → type cmd → Enter), and try again. Still nothing? Re-run the installer from nodejs.org/en/download and pick Repair if it offers it.

Install Claude Code

Now that Node.js is installed, you can install Claude Code with a single command. This downloads it from the internet and sets it up on your machine.

Before you start: Section 3 (Node.js) has to be finished first — this command uses npm, which arrives with Node.js. The official write-up of this step lives at docs.claude.com → Claude Code setup if you ever want the reference version.
Run this in Command Prompt (Start menu → type cmd → Enter — or reuse the window from the last step):
npm install -g @anthropic-ai/claude-code
On a company-managed computer: this command installs into your own user folder and doesn't need administrator rights, so it usually works even on locked-down machines. If it's blocked anyway, ask IT to allow it.
Verify it installed:
claude --version
If it says "'claude' is not recognized" — try these in order. One of them almost always does it.
  1. Close every Command Prompt window, open a fresh one, and run claude --version again. A window opened before the install can't see it.
  2. Confirm the install actually landed: run npm list -g @anthropic-ai/claude-code. If it prints nothing, run the install command above once more and read the output for red text.
  3. Still stuck? The official install and troubleshooting pages are docs.claude.com/claude-code/setup and .../troubleshooting.
Claude Code is installed. Two tools down, zero code written. That's about to change.

Create Your Workspace

Before you start building, you need a home base. Every project you build will live under one root folder: C:\dev. This keeps things organized and gives Claude Code a consistent place to work.

Why C:\dev? It's short, easy to type, and keeps all your work in one place. This same structure works across every project — each one is a folder under C:\dev. When you open a terminal and type cd C:\dev\MyProject, you're in your project. Clean and simple.
If C:\dev already exists, skip this step. If Windows won't let you create folders on C:\, create dev in your user folder instead (like C:\Users\YourName\dev) and use that path everywhere in this tutorial.
Your workspace is ready. Every project gets its own folder under C:\dev.

Make a one-click launcher (no more typing)

You just opened Command Prompt, typed cd C:\dev\Sandbox, then typed claude. You'll do that every single time you sit down to work. A batch file is a tiny text file that types those same commands for you. Double-click it and Claude opens, already standing in your project folder. No syntax to remember.

Turn on file extensions first (once). Windows hides the end of file names, which makes this step confusing. In File Explorer: View → Show → tick File name extensions. (On Windows 10 it's the View tab → tick File name extensions.) Now you can see whether a file really ends in .bat.

Build it. Open Notepad (Start menu → type notepad → Enter) and paste these three lines. If your project lives somewhere other than C:\dev\Sandbox, change the middle line right here in the box before you copy it — that's the only line you ever change.

Launch Claude.bat — editable

Line by line: @echo off keeps the window tidy, cd /d moves into your project folder (the /d lets it switch drives too), and claude starts Claude — exactly what you typed by hand.

Save it the right way. In Notepad choose File → Save As, then:

  • Go to your C:\dev folder (or your Desktop, if you'd rather it lived there).
  • Set Save as type to All files (*.*).
  • Type the file name Launch Claude.bat and click Save.
Watch for .txt on the end. If you leave Save as type on "Text documents", Notepad quietly saves Launch Claude.bat.txt, and double-clicking it just opens Notepad again. With file extensions turned on you'll spot it right away: rename the file and delete the .txt.

Test it. Double-click Launch Claude.bat. A black window opens and Claude starts, already in your project folder. Type exit when you're done, same as before.

Optional: a second launcher that picks up where you left off. Make another file the same way, name it Continue Claude.bat, and change the last line so Claude reopens your most recent conversation in that folder instead of starting fresh:
Continue Claude.bat — editable

Make it nice (all optional):

  • Desktop shortcut: right-click Launch Claude.bat → Send to → Desktop (create shortcut). On Windows 11, click Show more options first to find Send to.
  • Pin it to the taskbar: Windows won't pin a .bat file directly, so make a shortcut that runs it. Right-click an empty spot on the Desktop → New → Shortcut, paste the line below as the location, click Next, name it, and click Finish. Then right-click the new shortcut → Pin to taskbar (Windows 11: Show more options → Pin to taskbar).
cmd.exe /k "C:\dev\Launch Claude.bat"
  • Give it an icon: right-click the shortcut → Properties → Change Icon, and pick one you like.
  • Give it a friendly name: right-click the shortcut → Rename → call it Ask Claude.
  • One launcher per project: when you start a new project, copy the .bat file, rename the copy after the project, and change the folder line. One double-click per project.
On a Mac? The same idea is a .command file. Paste this one line into Terminal — it writes the launcher into your dev folder and marks it as something you're allowed to run. Change Sandbox if your folder is named differently. Then double-click Launch Claude.command in Finder.
printf '#!/bin/zsh\ncd ~/dev/Sandbox\nclaude\n' > ~/dev/"Launch Claude.command" && chmod +x ~/dev/"Launch Claude.command"
On Linux? Save the same three lines as a shell script (#!/bin/bash, then cd ~/dev/Sandbox, then claude) as ~/dev/launch-claude.sh, run chmod +x ~/dev/launch-claude.sh once, and run it from your file manager's "Run in Terminal" option. If you want it in your app menu, a small .desktop file with Terminal=true and Exec=bash -c "cd ~/dev/Sandbox && claude" does the job.
If it doesn't work:
  • The window flashes and closes: either claude isn't installed where Windows can find it (go back to Section 4 and check claude --version), or the folder name in the middle line has a typo.
  • It says "'claude' is not recognized": same fix — Section 4.
  • Your folder name has spaces in it: keep the quotes around the path, exactly as shown. Without them, Windows stops reading at the first space.

Put It Under Version Control

Git is your undo button and a free offsite backup. Set it up once — from here on, you just tell Claude to handle the Git work.

Don't want a GitHub account? There's a OneDrive route — skip to it at the bottom of this section. You get the backup, but not the undo button.
Install Git and the GitHub CLI in Command Prompt (Start menu → type cmd → Enter) — run these one at a time, then close and reopen the window. Both are free:
winget install --id Git.Git -e
winget install --id GitHub.cli -e
On a company-managed computer: if an install fails with "You cancelled the installation" (exit code 1602) and you didn't cancel anything, your IT security policy declined it for you. Add --scope user to the end of each command to install without administrator rights. If that's blocked too, ask IT to install Git and the GitHub CLI.
If Command Prompt says "'winget' is not recognized" — your Windows doesn't have the package manager. Skip the commands above and use the regular installers instead, one at a time, clicking Next through the defaults: Git for Windows · GitHub CLI. Then close and reopen Command Prompt and carry on with the next step. (If you'd rather have winget itself, it ships with Microsoft's App Installer — details at Microsoft's winget page.)
Connect to GitHub (once). Run the command below in Command Prompt — it asks a few questions one at a time, right there in the terminal:
gh auth login
Answer: GitHub.com → HTTPS → Yes (authenticate Git) → Login with a web browser. It then shows a one-time code — press Enter, your browser opens, and you paste the code there.

Now let Claude do the rest. From your project folder, start claude again — just like the last section — and say:

Put this project on GitHub as a private repository.
Private, not public for anything with client data or API keys — and never commit secrets. After any good chunk of work, tell Claude "save my progress to GitHub."
You've got a safety net now. Break something? "Claude, undo my last change." Lose your laptop? Your work is on GitHub.
No GitHub? Back up to OneDrive instead. If your computer already signs in to OneDrive, you can skip everything above in this section. Know the trade: OneDrive is a backup, not an undo button. It can bring a lost file back; it can't roll a whole project back to how it was on Tuesday.

Keep working in C:\dev and let Claude keep a copy in OneDrive. From C:\dev, start claude and say:

Back up my C:\dev folder to my OneDrive with a copy that runs every day. I keep working in C:\dev. Skip node_modules and other tool folders.
Copy, don't move. Don't drag C:\dev itself into the OneDrive folder. OneDrive grabs files while they're being written, and tools that write thousands of small files will grind the sync to a halt.

One more thing lives outside C:\dev: your global Claude folder, C:\Users\[you]\.claude. It holds your CLAUDE.md (next section), your settings and what Claude has learned about each project. Back up only C:\dev and a dead laptop gives you your work back with a Claude that has never met you. So add:

Add my global Claude files to that backup: CLAUDE.md, settings.json, the memory folders and any skills or commands from my .claude folder. Copy only. Leave the folder where it is and leave out the credentials file.
The live .claude folder stays put. It also holds your sign-in and files that change every second, so it should never be moved into OneDrive or synced whole. A copy of the handful of files above is all you need.
Going this way? Tick the four boxes above once Claude shows you the copy sitting in your OneDrive, then carry on to the next section.

Your CLAUDE.md — Teaching Claude How to Work With You

Here's the most important concept in this entire tutorial:

Claude doesn't remember you between sessions. Every time you type claude and start a new conversation, it's like meeting a brilliant contractor who has total amnesia. It has no idea who you are, what you've built before, or how you like to work. CLAUDE.md fixes that.

A CLAUDE.md is a plain text file Claude Code reads automatically when it starts — before you say a word. It's your instruction manual for Claude, and it comes in two levels. The global one lives in your user profile (C:\Users\[you]\.claude\CLAUDE.md) and applies to every project on your machine — who you are and how you work belongs there, written once. A project CLAUDE.md sits at a project's root and adds rules for that one project only ("this app is a single HTML file, no server") — you'll create your first of those in Exercise 1. Right now, we're making the global one.

Without a CLAUDE.md, Claude is a generic assistant. With one, Claude is your assistant.

What goes in a CLAUDE.md?

Write this one in your own words. CLAUDE.md is how Claude learns who you actually are, so a file copied from somebody else quietly teaches Claude to expect somebody else — that's worse than having no file at all. The builder below asks you a few plain questions and assembles the file out of your answers. Nothing is filled in for you; the grey text inside each box is only an example of the kind of answer, and it disappears the moment you start typing.

A sentence or two. This is what makes Claude's answers fit your world instead of a generic one.

Be honest here. It changes how much Claude explains.

Our crew schedule is a whiteboard that gets erased every Friday. I
want a spreadsheet that shows who is on which job, and prints
clean enough to hand to a foreman.

## How We Work

Explain what you are doing as you go, so I learn while we build.

1. I give you the requirements.
2. You propose a plan and wait for my approval.
3. On approval, you deliver complete working files.
4. I test it and confirm.

Ask first, do not run ahead. When something breaks, gather
information before changing code.

## Always

- Show me the whole file, not just the part that changed
- Use the crew names we actually use, not Crew A and Crew B
- Tell me when something did not work

## Never

- Never delete a file without asking me first
- Never hand me something half finished and call it done

C:\dev

- Tell me to use /clear after heavy work or big file reads.
- When in doubt, /clear. Ten seconds beats losing the session.

        

      

    


    
What a mature CLAUDE.md looks like:

    
A mature CLAUDE.md has all of the above plus some extras that evolve out of daily use:

    
    
      
  • A "Brown M&M" rule — a small test at the top of your file that forces Claude to prove it actually read the instructions. (Van Halen used to put "no brown M&Ms" in their concert riders to verify promoters read the whole contract. Same idea.) If Claude skips the test, you know it skipped the file.
    • 
      
  • Naming conventions — rules about how to name variables and database fields so everything stays consistent
    • 
      
  • "Archive, don't delete" — instead of deleting old files, move them to an archive folder. You never lose work.
    • 
      
  • "Claude runs commands" — Claude executes terminal commands itself instead of telling you to do it. You shouldn't have to touch the terminal for routine tasks.
    • 
    


    
Other consultants might add rules like:

    
    
      
  • "All client-facing documents use our company letterhead"
    • 
      
  • "Use metric units, not imperial"
    • 
      
  • "My clients speak Spanish — build bilingual interfaces"
    • 
      
  • "I'm working on a Mac, not Windows"
    • 
    


    
The CLAUDE.md grows over time. Every time Claude does something you don't like, add a rule. Every time it does something great, add a rule to keep doing it. It's a living document.

Your context/ folder — Scope and Journal

  

  

    
Your global CLAUDE.md tells Claude who YOU are. Now you need to tell Claude what you're BUILDING and what's HAPPENED so far. Both of those live in a single folder called context/ at the root of your project.


    

      Two files do the work:
      
    
        
  • context/PROJECT.md — the project brief. What are you building, who is it for, what's the stack, what's done, what's next.
    • 
        
  • context/JOURNAL.md — the running log. At the end of every session, you ask Claude to add a dated entry: what we did, what worked, what's next.
    • 
      

      Claude reads both at the start of every session. You never have to re-explain the project or where you left off.
    


    
Why two files instead of one? PROJECT.md is the current state — short, kept up to date, rewritten as the project evolves. JOURNAL.md is the history — dated entries that pile up, newest first. One file would either get too long for Claude to read every session, or lose the history every time you updated the scope. Two files keep each one focused.


    
Here's a simple PROJECT.md. Don't create this one — we'll make real ones in the exercises.


    

      Example context/PROJECT.md
# Project: Client Intake Form

## Goal
Build a web form that new clients fill out before their
first meeting. Responses get emailed to me.

## User
My clients. Non-technical. They'll open this in a browser
on their phone or computer.

## Tech
- Single HTML file (no server needed for the form itself)
- Google Apps Script backend for email delivery

## Status
Form layout done. Email backend in progress.

## Constraints
- Must work on mobile
- Must save progress if they close the tab (localStorage)
- Must look professional, not like a government form


    
And here's a JOURNAL.md after a few sessions:


    

      Example context/JOURNAL.md
# Journal

Newest first.

## 2026-04-15
- Built the form layout (intake.html)
- Added localStorage so progress saves automatically
- NEXT: wire up Google Apps Script for email delivery

## 2026-04-14
- Created project folder and CLAUDE.md
- Sketched out the form fields with Claude
- Decided on single-HTML-file approach (no server)


    
How to maintain JOURNAL.md: at the end of every session, before you type exit, say this to Claude:


    

      Update context/JOURNAL.md with what we did today. Include decisions, what works, what doesn't, and what's next.
      
    


    
That's it. Claude appends a dated entry. Next session, Claude reads both files and picks up exactly where you left off.


    

      About the older "three-file methodology." Earlier versions of this tutorial taught PROJECT.md and MEMORY.md at the project root. The new model puts both in a context/ folder and renames MEMORY.md to JOURNAL.md — that's because Claude has its own built-in memory system in your user profile (covered on the harness page) with a file also called MEMORY.md, and the collision was confusing. Same idea, sharper boundary: project state lives in the project (context/); facts about you live in the harness.
    


    

      
      
    


    
The Foundation
Every project you build will have a CLAUDE.md at the root for project rules and a context/ folder with PROJECT.md and JOURNAL.md — while your global CLAUDE.md covers who you are. That's the foundation. You'll add other folders (source/, output/, reference/, archive/) as projects grow. Everything else is just typing.

Connect Your Bank (optional)

  

  

    
Optional, and not part of your score. The basics are done once Section 9 is ticked. Do this one only if you want your Claude to look at your bank and card activity for you. Skipping it costs you nothing.


    
Once Claude can see your bank activity, it can do things like check your books against the bank, flag a charge you don't recognize, or tell you what cleared last week, without you downloading a single statement. The service that makes that possible is called SimpleFIN Bridge.


    

      What SimpleFIN Bridge is, in plain words:
      
    
        
  • A small paid service at simplefin.org that lets your Claude read your bank and card activity: balances and transactions.
    • 
        
  • It is read-only. Nobody can move money, pay a bill or change anything with it.
    • 
        
  • It costs around 50 cents per bank per month. Prices change, so check their pricing page before you sign up.
    • 
        
  • It refreshes about once a day. It is not a live, to-the-minute feed.
    • 
        
  • It only has data from the day you connect forward. It cannot go back and fetch last year. Connect early if you want history to build up.
    • 
        
  • Your bank password is typed into SimpleFIN Bridge when you connect, and is not inside the link your Claude uses.
    • 
      

    


    
The honest caveats. SimpleFIN Bridge is a small service, mostly used by personal-finance apps. Not every bank connects, and some connect only some of their accounts. The only way to know is to try yours. If yours doesn't connect, you've lost very little: stop here and carry on with the exercises.


    
Treat the access link like a password. When you set this up, SimpleFIN gives you an access link. Whoever holds that link can read every connected account until you turn it off. So: never paste it into a chat (including this one with Claude), a document, an email or a note, and never keep it in a shared or cloud-synced folder (OneDrive, Dropbox, Google Drive) or on GitHub. It lives in one file on your computer and nowhere else.


    
Keep an access log

    
Here's the habit that makes this safe: your Claude never talks to SimpleFIN directly. Every call goes through one small program, simplefin_pull.py, that writes a row in a log on your computer before each call: the time, the computer's name, your internet address, who asked and why, and what was pulled. If you ever wonder "was that me?", the log answers it.


    
1. Make a folder for it. Inside your project folder, make a folder named simplefin (so it ends up as C:\dev\<your project>\simplefin\). Or just tell Claude:

    

      Make a folder called simplefin in this project. I'm about to save a program into it called simplefin_pull.py.
      
    


    
2. Save the program into that folder as simplefin_pull.py, exactly as written. Click Download (then move the file from your Downloads folder into simplefin), or open the code, click Copy, paste it into Notepad and save it with Save as type: All files, the same way you made the launcher. It uses plain Python with nothing extra to install. If you don't have Python yet, ask Claude to check and install it for you.

    

      Show the code (simplefin_pull.py)
      
simplefin_pull.py — save exactly as written

    

    
The program also keeps the data each pull brings back in a pulls folder next to it, so Claude can work from a saved copy instead of calling the bank again.


    
3. Keep the link out of GitHub and out of the cloud. The access link will live in a file called .env in the simplefin folder. Tell Claude:

    

      Add simplefin/.env and simplefin/pulls/ to this project's .gitignore so they never go to GitHub. If this project folder is backed up or synced to OneDrive or anywhere else, change that so simplefin\.env is left out, and show me it is.
      
    


    
4. Teach Claude the rule, so it holds in every future session. Tell Claude:

    

      Add this rule to this project's CLAUDE.md: Only ever reach SimpleFIN through simplefin\simplefin_pull.py, always say why with --why, never open, print or copy simplefin\.env, and pull once for what you need instead of repeating pulls.
      
    


    
Connect your bank

    
    
      
  • Open your own account at simplefin.org and follow their sign-up.
    • 
      
  • Connect each bank and card you want Claude to see, one at a time. You type the bank login into SimpleFIN Bridge yourself; Claude never sees it. If this is for your business, connect business accounts only.

  • Make a setup token in your SimpleFIN Bridge account. A setup token is a long code that works once: the program trades it for the access link.
    • 
    


    
Claim the token yourself, not through the chat. Open a fresh Command Prompt (Start menu → type cmd → Enter), go to the simplefin folder, and run the claim. Change Sandbox if your project has a different name.

    

      cd /d "C:\dev\Sandbox\simplefin"
      
    

    

      python simplefin_pull.py claim
      
    

    
Paste the setup token when it asks and press Enter. Nothing shows while you paste. That's on purpose. It says "Done" and saves the access link in .env. Neither you nor Claude ever needs to look at that link again. (On a Mac, type python3 instead of python.)


    
Test one pull. Back in Claude, say:

    

      Run python simplefin_pull.py accounts --balances-only --why "First test pull" in the simplefin folder, then show me the log with python simplefin_pull.py log.
      
    

    
You should see each account and its balance, then a log with two rows (the claim and the test pull), each saying ok. Every call from now on adds a row, before it happens.


    
"SimpleFIN emailed me that my data was accessed"

    
SimpleFIN can email you when your data is read. Most of the time it was you. To check:

    
    
      
  • Open the log. Ask Claude: "show me the SimpleFIN log" (it runs python simplefin_pull.py log).
    • 
      
  • Find a row at the time in the email. The email may use a different time zone; every log row shows its time zone.
    • 
      
  • Compare the internet address in the email with the public_ip in that row.
    • 
      
  • They match: it was you. Nothing to do.
    • 
      
  • No row at that time, or a different address: treat it as someone else. Turn the link off now and make a new one (next part).
    • 
    

    
Your internet address changes when you work from home, a hotel or a phone hotspot. If the time matches and the row shows your computer and your user name, that's still you.


    
Lock it and make a new link

    
Use this if the log doesn't explain an email, or any time you want a fresh link. Nothing is lost, and because the link is read-only, nobody could have moved money with the old one.

    
    
      
  • Turn off the old link. Log in to your SimpleFIN Bridge account, find the app connection this link belongs to, and revoke or disable it. That ends the old link at once.
    • 
      
  • Make a new setup token, the same way you made the first one.
    • 
      
  • Claim it with the program in your own Command Prompt, in the simplefin folder:
    • 
    

    

      python simplefin_pull.py claim --replace
      
    

    
    
      
  • Test one pull through Claude, the same as before, with --why "Test after making a new link".
    • 
      
  • Look at the log and check the new rows say ok.
    • 
    


    
The weekly habit

    
Once a week, ask Claude "show me this week's SimpleFIN log" and read it: how many calls, from which computer, for what. Anything you don't recognize, run the email check above. Look at it every week and an alert email is never a surprise.
